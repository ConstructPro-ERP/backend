# How Schema Updates Actually Work — Plain English

This document explains what each file does, what each command does, and answers
"do I need to touch apply-schema.sql manually?"

---

## The three files you need to understand

```
prisma/schema.prisma          ← what you WANT the database to look like
prisma/schema.applied.prisma  ← what the database looks like RIGHT NOW
scripts/apply-schema.sql      ← the SQL instructions to get from NOW → WANT
```

Think of it like this:

- `schema.prisma` is your **target**.
- `schema.applied.prisma` is your **current state snapshot**.
- `apply-schema.sql` is the **change instructions** generated by comparing the two.

---

## Do you ever manually edit `apply-schema.sql`?

**No. Never.** You never write or edit `apply-schema.sql` by hand.

It is always generated automatically by running:

```powershell
npx prisma migrate diff --from-schema prisma/schema.applied.prisma --to-schema prisma/schema.prisma --script -o scripts/apply-schema.sql
```

That command reads both schema files, figures out what SQL is needed to go from
the current state to the target state, and writes it into `apply-schema.sql`.

You only **read** `apply-schema.sql` to double-check the SQL before applying it.

---

## What each step does — explained simply

### You edit `prisma/schema.prisma`

This is the only file you write yourself when making a schema change.
You add a new model, a new field, a new enum — whatever you need.

At this point the database has NOT changed yet. You have only changed a text file.

---

### You run `prisma migrate diff`

```powershell
npx prisma migrate diff --from-schema prisma/schema.applied.prisma --to-schema prisma/schema.prisma --script -o scripts/apply-schema.sql
```

This command:
1. Reads `schema.applied.prisma` — "what is currently in the database"
2. Reads `schema.prisma` — "what you want"
3. Calculates the **difference** between the two
4. Writes the SQL needed to apply that difference into `scripts/apply-schema.sql`

No database connection is made. It is just comparing two text files.

**Example:** if you added a `Notification` model to `schema.prisma` but
`schema.applied.prisma` does not have it, the diff will produce:

```sql
CREATE TABLE "Notification" (
  "id" TEXT NOT NULL,
  "userId" TEXT NOT NULL,
  "message" TEXT NOT NULL,
  "read" BOOLEAN NOT NULL DEFAULT false,
  "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
  "updatedAt" TIMESTAMP(3) NOT NULL,
  CONSTRAINT "Notification_pkey" PRIMARY KEY ("id")
);
```

At this point the database still has NOT changed. You have only generated a SQL file.

---

### You review `scripts/apply-schema.sql`

Open the file and read it. Check that it only contains what you expect.

Things to look out for:
- A `DROP TABLE` or `DROP COLUMN` you did not intend — this destroys data.
- A `◇ injected env ...` line at the very top — this is not SQL, delete it.
- An `ALTER COLUMN ... SET NOT NULL` on a column that already has data — this
  can fail if existing rows have nulls in that column.

If you used the `-o` flag (as shown above), the dotenvx header issue does not
occur — only the SQL is written to the file.

---

### You run `node scripts/run-migration.mjs`

```powershell
node scripts/run-migration.mjs
```

This script reads `apply-schema.sql` and executes each SQL statement against
your NeonDB database one by one, using the Neon serverless driver (port 443,
not port 5432).

For each statement it prints:
- `✓` — applied successfully
- `⚠ skipped (already exists)` — already there, no problem
- `✗ FAILED` — something went wrong, the script stops

At this point the **database has changed**.

---

### You update `schema.applied.prisma`

```powershell
Copy-Item prisma/schema.prisma prisma/schema.applied.prisma
```

This copies your current `schema.prisma` over `schema.applied.prisma`.

**This step is critical.** If you skip it, the next time you run `migrate diff`
it will compare against the old snapshot and generate SQL for changes that are
already in the database — causing "already exists" errors or worse.

After this copy, the two files are identical, which represents "the database
matches the schema".

---

### You run `npx prisma generate`

```powershell
npx prisma generate
```

This regenerates the Prisma TypeScript client so your application code gets the
updated types. If you added a `Notification` model, after this step you can use
`prisma.notification.create(...)` in your code.

---

## Complete picture — one diagram

```
schema.applied.prisma          schema.prisma
(current DB state)             (what you want)
        │                             │
        └──────── migrate diff ───────┘
                       │
                       ▼
              apply-schema.sql
              (generated SQL)
                       │
                 (you review it)
                       │
                       ▼
            run-migration.mjs
            (applies SQL to DB)
                       │
                       ▼
         Copy-Item schema.prisma
                schema.applied.prisma
         (snapshot now matches DB)
                       │
                       ▼
            prisma generate
         (client types updated)
```

## Common mistakes

### Mistake 1 — Running migrate diff twice without applying

If you run `migrate diff`, then make more edits to `schema.prisma`, then run
`migrate diff` again, the second run overwrites `apply-schema.sql`. The first
SQL is gone. This is fine — you just get a fresh diff that covers all your
changes at once.

### Mistake 2 — Forgetting to update `schema.applied.prisma`

If you apply the migration but do not copy `schema.prisma` over
`schema.applied.prisma`, the next `migrate diff` will see a "diff" for things
that are already in the database. The migration script will hit "already exists"
warnings, which are safe, but it is messy and confusing.

### Mistake 3 — Editing `apply-schema.sql` by hand

Do not do this. If there is a problem with the SQL, fix `schema.prisma` (or
`schema.applied.prisma` if the snapshot is wrong) and regenerate the SQL.

### Mistake 4 — Using `>` instead of `-o`

```powershell
# BAD — PowerShell writes UTF-16 LE, PostgreSQL rejects it
npx prisma migrate diff ... --script > scripts/apply-schema.sql

# GOOD — -o writes clean UTF-8 SQL only
npx prisma migrate diff ... --script -o scripts/apply-schema.sql
```

---

## Summary

| File | Who writes it | When |
|---|---|---|
| `schema.prisma` | You | When you make a schema change |
| `apply-schema.sql` | `migrate diff` command | Automatically, every time you generate |
| `schema.applied.prisma` | You (via Copy-Item) | After every successful migration |

The only files you ever write by hand are `schema.prisma` and the copy command
that updates `schema.applied.prisma`. Everything else is generated or automated.
